# QBO 08 — Opening TB import, opening open items, JE CSV import — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a firm bring a client's starting position and bulk journals in from a spreadsheet — opening trial balance,
A/R / A/P invoices outstanding at books start, and multi-line journal entries — with tolerant parsing (fuzzy account
map with a confirm step, negative amounts, date-format detection) where QBO's importers were brittle.

**Architecture:** Pure parsing / mapping / validation in `services/accounting/importing.py` (primitives) and
`services/accounting/import_rows.py` (the three importers' row builders), tested without a DB. One router,
`routers/accounting_imports.py`, exposes a stateless preview → confirm pair per importer (the browser re-sends the file
with the person's mapping choices; the server re-parses and re-validates on confirm) plus template downloads. Writes go
through the existing mechanisms: the opening TB is the company's `kind="opening"` journal entry; imported journals are
`kind="manual"` entries validated by the same checks as the JE form; opening open items are a new table
`aa_opening_items` that the books engine, the subledger and the bank matcher see as pre-books-start sales / bills.

**Tech Stack:** FastAPI, SQLAlchemy async, openpyxl (already a dependency; `payroll_import.parse_sheet` reads
CSV / XLSX with zip-bomb and row limits), difflib for fuzzy names, Next.js + TS for the UI.

**Spec:** `2026-10-16-quickbooks-parity-plan.md` §1 ("Imports are brittle") and §3 "P2 — Opening balances and CSV
import"; program rules in `2026-10-16-qbo-parity-program.md`.

## Global Constraints

- Branch `qbo-parity`; commit after each green task; messages end with the two attribution lines.
- FORCE RLS on the new table (add to `_FIRM_TABLES` in `services/accounting/rls.py`); `enterprise_id` filter on every

- `csv_safe` on every cell of generated XLSX / CSV (templates).
- Limits: file ≤ 5 MB, ≤ 5000 data rows (`payroll_import.MAX_ROWS`), ≤ 500 journal entries per import, ≤ 200 lines per
  entry (schema limit), ≤ 2000 open items per import.
- Locked / inactive accounts are refused (same messages as the JE form via `locked_message`).
- Only owners / managers import (`MANAGER_ROLES`), like the chart and employee import.
- Every confirm writes audit events (`entity` `journal_entry` / `opening_item`, action `import`).
- UI: theme CSS vars, `Hint` on the page, tour line, `seg()` for every path id.

## Review Focus

1. A TB exported from another system with a "Total" row and blank lines → total row skipped, not posted twice
   (test `test_tb_skips_total_rows`).
2. Dates like `03/04/2026` where every value fits both MM/DD and DD/MM → ambiguous, preview asks, override honoured
   (test `test_detect_date_format_ambiguous` + `test_je_rows_use_override_format`).
3. Amounts with thousands separators, `₱`, parentheses, trailing `CR` / `DR` → parsed with the right sign
   (test `test_parse_amount_variants`).
4. Same account appearing twice in a TB (split rows) → merged into one line (test `test_tb_merges_duplicate_accounts`).
5. Opening open items dated on/after the books start → refused per row (they belong as real documents) (test
   `test_open_items_refuse_dates_after_books_start`).

## Tasks

### Task 1: Parsing primitives (`importing.py`)

**Interfaces — Produces:**
- `parse_amount(text: str) -> Decimal | None` — strips `₱`, `PHP`, commas, spaces; `(x)` and leading `-` negative;
  trailing ` CR` negative, ` DR` positive; blank / `-` → None; bad → `ValueError`.
- `DATE_FORMATS: tuple[str, ...]` (strptime formats incl. `%Y-%m-%d`, `%m/%d/%Y`, `%d/%m/%Y`, `%m/%d/%y`, `%d/%m/%y`,
  `%Y/%m/%d`, `%d-%b-%Y`, `%d %b %Y`, `%b %d, %Y`, `%B %d, %Y`, `%m-%d-%Y`, `%d-%m-%Y`, `%d.%m.%Y`).
- `detect_date_format(values: list[str]) -> tuple[str | None, list[str]]` — (chosen, candidates): candidates = formats
  that parse every non-blank value (ISO timestamps `YYYY-MM-DD…` from XLSX count as ISO); chosen = the only one, or
  `None` when several fit (ambiguous) or none.
- `parse_date(text: str, fmt: str) -> date` (ValueError on mismatch).
- `suggest_columns(headers: list[str], synonyms: tuple[tuple[str, str], ...]) -> dict[str, str]` — field → header.
- `AccountRef(code, name, active, locked)`; `AccountMatch(code: str | None, how: str, score: float,
  alternatives: list[str])`, `how` ∈ `code | name | fuzzy | none`.
- `match_account(code: str, name: str, chart: list[AccountRef]) -> AccountMatch` — exact code (also a leading code
  inside the name cell, "1020 Cash in bank"); then normalised name (lowercase, punctuation → space, `&`→`and`,
  collapse spaces); then difflib ratio ≥ 0.72 (best; alternatives = next 3 ≥ 0.5). Inactive / locked accounts still
  match (the row then errors) so the person sees why.
- `source_key(code: str, name: str) -> str` — `f"{code.strip()}|{norm(name)}"`, the key the person's overrides use.

### Task 2: Row builders (`import_rows.py`)

**Interfaces — Consumes:** Task 1. **Produces:**
- `RowIssue(row: int, message: str)`.
- `TB_FIELDS`, `OPEN_FIELDS`, `JE_FIELDS` (field → label) and synonym tables; `TEMPLATES: dict[str, (headers, rows)]`
  for `opening-tb`, `open-items`, `journal-entries`.
- `build_tb(headers, rows, columns: dict[field, header], chart: list[AccountRef], overrides: dict[source_key, code],
  date_format: str | None) -> TbResult` with `lines: list[(code, debit, credit)]` (merged per account, zero nets
  dropped), `rows` (per input row: row no, code/name in, debit, credit, matched code, how), `accounts`
  (distinct source → AccountMatch + chosen), `debit`, `credit`, `difference` (debit − credit), `as_of: date | None`,
  `errors: list[RowIssue]`, `warnings: list[str]`. A row with both debit and credit nets; a negative debit is a
  credit and vice versa; a single signed `balance` column is debit if positive. Rows without code and name, or whose
  name starts with "total" and has no code, are skipped.
- `apply_difference(lines, difference, account) -> lines` — adds the balancing line.
- `build_open_items(headers, rows, columns, books_start: date, default_kind: str | None, date_format) -> OpenResult`
  with `items: list[OpenItemIn]` (`kind ar|ap`, contact_name, contact_tin (digits, 9), doc_number, doc_date, due_date,
  terms_days, amount), errors (missing name / date / amount, date ≥ books_start, amount = 0, unknown type), totals
  per kind. Kind from a "type" column (`AR`, `receivable`, `customer`, `invoice` → ar; `AP`, `payable`, `supplier`,
  `bill` → ap) or `default_kind`.
- `control_tie(totals: dict[kind, Decimal], control: dict[kind, Decimal]) -> list[str]` — warning per kind when the
  open items don't equal the opening TB's control balance (A/R debit, A/P credit, incl. existing items).
- `build_journals(headers, rows, columns, chart, overrides, date_format, books_start) -> JeResult` with `entries:
  list[JeDraft(key, entry_date, reference, particulars, is_adjusting, book, lines)]` and errors per entry (unbalanced
  with the amounts, < 2 lines, before books start, unmapped / inactive / locked account, > 200 lines) and per row
  (bad date / amount). Grouping: `journal_no` column when mapped, else `(date, reference)`; a row without a group
  continues the previous row's entry (blank date / no lines). Signed `amount` column alternative to debit / credit.
  Adjusting flag: yes / y / 1 / true / x / AJE.

## Decisions

1. **Opening open items are their own table, not documents.** A synthetic `aa_documents` row would need a file, open
   in the document panel and — dated in a prior quarter — leak into that quarter's returns if anyone generated it.
   `aa_opening_items` rows enter the books as pre-books-start sales / bills (no document entry, so the opening TB's
   A/R / A/P is not doubled) and only their payments post (Dr bank/cash, Cr A/R; Dr A/P, Cr bank/cash).
2. **Tie to the control account is a warning, not a block.** Firms often carry A/R with items they can't list yet.
   The preview and the Import page show "Open A/R items ₱x vs opening A/R ₱y (difference ₱z)".
3. **Receipts (OR scans) don't link to opening items** in this workstream: `settles_document_id` is a foreign key to
   documents and ~40 call sites split receipts on it. Bank lines match opening items (they are candidates like any
   invoice), and a person can record a cash / bank payment on the item itself ("Record payment"). An OR received for
   an opening invoice should be excluded with that reason after recording the payment. Left for the owner.
4. **Bank window:** opening items enter the matcher dated the day before the books start (the −7/+90-day window
   would otherwise miss old invoices paid in the first months).
5. **Opening TB import replaces** the company's opening entry lines (one opening entry per company is an existing
   rule); the preview says so when one exists. The as-of date is informational: a TB not dated the day before the
   books start (or the books start) gives a warning; the opening entry always sits on the books start.
6. **Out of balance:** refused unless the person explicitly picks an account for the difference (no default; the
   picker lists equity accounts first). Locked / inactive accounts can't be picked.
7. **Closed months (JE import):** allowed, through the existing mechanism — the engine posts a change to a closed month
   as a correcting entry on the first open day (as the JE form and Reclassify already do). The preview marks each
   such entry "posts as a correction on <date>".
8. **Ambiguous dates:** when every value fits both MM/DD and DD/MM the preview isn't ready until a format is chosen;
   the select lists the fitting formats with MM/DD first (PH convention). XLSX date cells arrive as ISO.
9. **Stateless preview / confirm:** nothing is stored between the two calls; the confirm re-parses the file with the
   person's choices and must reach `ready` again.
10. **Account-name only rows** that match nothing stay unmapped (error) — never auto-created in the chart.
